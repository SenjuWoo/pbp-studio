PBP STUDIO - HOW IT WAS MADE / FORMAT NOTES
==========================================

Goal: make custom Castle Crashers characters for the "Painter Boss Paradise" DLC as easily as
possible, with local AI doing the heavy lifting.

1) THE FORMAT (verified against the installed game)
--------------------------------------------------
- A local custom character is a folder containing:
  - painting.png : 2048x2048 RGBA texture atlas, the official template with the user's art
  - pbp.xml      : <character displayname="NAME"><magictype>N</magictype></character>
- The shipped sample lives at:
  CastleCrashers\data\pbplocal\violet\{painting.png, pbp.xml}
- The game's own pbp.xml may omit <magictype> entirely (that means "default magic").
- Workshop items are a single "PKTB" container (steamapps\workshop\content\204360\<id>\): the game's
  own pack format with an encrypted painting.png and a compressed+encrypted pbp.xml. Publishing and
  validation are done by the game itself, so PBP Studio stops at producing the local folder.

2) TEMPLATE LAYOUT (region map) - exact boxes
---------------------------------------------
- The 39 draw boxes are the 39 transparent connected components of the template (alpha < 16). They
  form a regular grid: 7 heads 234x332, 5 bodies 234x258, sword 96x258, shields 90x130, 6 giant
  torsos 292x296 / 270x296, 15 limbs (rows of 8 / 4 / 3), hudicon 130x130, select banner 258x514,
  backoffb figure 258x514. app/regions.py stores them in template reading order.
- Versions up to 0.7.2 used rects that were the wireframe's own footprint (about 60 % of the real
  box), which is one reason the art looked tiny and misplaced. 0.8.0 uses the exact boxes.
- Box roles were mapped to sprite names found in the game executable's string table:
  helm/helm2..5/helm.A/helm.B (7 heads), pbod1/pbodland/knightbodrun/pbodspin/pbodback (5 bodies),
  sword, shield1, shield2, bigbod1..4/bigbodback/bigbod911 (6 beefy bodies),
  bigarm1..9/bigleft1/bigleft2/bighand1/bigarmgrap/bigarmthro/bigarm911 (15 limbs),
  hudicon, selectbanner, backoffb (3 UI art boxes).

3) WHAT REAL WORKSHOP CHARACTERS LOOK LIKE (measured on 37 decoded atlases)
----------------------------------------------------------------------------
- Every head box holds ONE head, at the same place: x 24-78 %, y 47-89 % of the box (bottom anchored).
- Bodies are a small torso garment only (no head, no legs): x 35-66 %, y 66-94 %.
- The sword box holds one vertical weapon; shield1 a small item; shield2 its thin edge.
- Giant boxes hold a headless, armless round torso in the character's clothing colours.
- Most creators leave the 15 beefy limbs as the template's dark default art.
- hudicon and selectbanner are full-bleed illustrations; backoffb is a figurine on a blue base.
- These medians ship as app/layout_stats.json (numbers only). The atlases themselves are third-party
  art: they were only analysed locally and are never part of this repository.

4) WHY THE OLD "PER-BOX IMG2IMG" PIPELINE FAILED (0.1-0.7)
-----------------------------------------------------------
- Each box was repainted independently, so there was no shared identity (hair, colours, trim drifted),
  and models filled a box with several small figures (collages).
- The ControlNet guide never reached SwarmUI: the app sent "controlnetimage", SwarmUI's id is
  "controlnetimageinput", so the unknown field was ignored and the init image was traced instead.
- Fixes in 0.8: one master design, edit-model redraws that reference it, exact boxes, real placement
  targets, quality gates, and the correct ControlNet parameter for the Anima-only model.

5) THE 0.8 PIPELINE
-------------------
- Master: Anima (txt2img, 1024) from the user's text, or the user's own image.
- Edit backends (Flux.2 Klein 4B fp8, or Qwen Image 2.1 turbo int8) receive the master as a reference
  image and a text command per piece ("head ... turned in three-quarter view, face turned to the right").
  Edit models follow text pose commands well but ignore abstract helmet sketches, so poses come from text.
- Bodies and giants go through a torso-reference piece first (master -> torso garment -> poses), which
  carries the clothing colours; a colour-histogram gate (Bhattacharyya >= 0.70 against the reference;
  measured good 0.81-0.99, wrong colours 0.57-0.62) and an aspect gate reject wrong pieces and retry.
- Landing, running, spinning, the lying and falling giants and the shield edge are derived from other
  pieces by squash / rotate; this is deterministic and consistent.
- cut_out: white canvas -> alpha with a black soft edge (outlines are black, so alpha = darkness).
- fit: scale to the median real bbox, bottom-anchored for heads/bodies/giants/figure.
- Limbs keep the template art.

6) MAGIC TABLE
--------------
- castle.exe contains an ordered magic name table; the DLC chooser shows 26 of these names.
- pbp.xml <magictype> indexes that table (0-based). The shipped violet template uses 1, which is
  "Default Magic" in the extracted order, matching the game default.
- app/magics.py holds the table + the in-game chooser order used by the UI grid.

7) LOCAL AI BACKEND
-------------------
- SwarmUI (or anything exposing its HTTP API) on http://localhost:7801.
- API used: POST /API/GetNewSession, /API/GenerateText2Image (promptimages = reference images joined
  with "|"; controlnetimageinput for ControlNet), /API/ListModels, /API/ListBackends.
- The response lists images as "View/<user>/raw/<date>/<file>.png"; the file lands in
  <SwarmRoot>/Output/<user>/raw/<date>/<file>.png. SwarmUI may answer a moment before the file is
  flushed, so the client waits and falls back to the newest png.
- If SwarmUI answers "No backends available" its ComfyUI backend died: POST /API/RestartBackends
  {backend: "all"} and wait for status "running".

8) SERVER / UI
--------------
- app/server.py: stdlib ThreadingHTTPServer on 127.0.0.1:8777, JSON API + static files.
  Endpoints: /api/status, /api/magics, /api/job (GET poll, POST start), /api/cancel, /api/settings,
  /api/master (upload your own design image), /api/check-backend, /api/start-backend, /api/pick-folder,
  /api/open-folder, /api/install-to-game, /api/redownload-template, /api/file (allow-listed files).
- app/static/: vanilla HTML/CSS/JS, no build step, no external assets.
- Jobs run in a worker thread; the page polls /api/job and shows the live atlas preview + log.

9) TESTING
----------
- py -3 -m pytest : offline suites (pipeline helpers, fake-SwarmUI end-to-end run on a synthetic
  template, request payload names, settings, XML, server guard).
- tools/bench.py runs a full job from the command line for backend comparisons.
- Not yet verified live in game by the author: hot reload of a generated folder and the exact
  <magictype> numbering (single manual tests; see STATE.md).
